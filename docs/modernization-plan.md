# RayTab 技术替换与界面改造实施方案

方案日期：2026-10-02；本地验收日期：2026-10-03。状态：源码实施与本地验收完成。本文件保留初始方案和后续交付记录；实际发布状态以仓库标签及 Releases 为准，本地验收不表示远端发布已完成。

本方案覆盖本次讨论的成熟技术替换、网站图标、设置界面和右键菜单。持续目标以完整交付为终点；按阶段完成全部覆盖、旧机制清理与验证，不以部分接入作为完成。

2026-10-03 追加的产品定位是“以网站图标管理为核心、简洁流畅的开源新标签页”。以 [产品定位](product-direction.md)、[设置逐项决策](research/settings-decisions.md)、[界面基准](ui-reference.md) 和 [当前验收](modernization-validation.md) 为准；此前的 iTab 复刻方案已停止，旧阶段的具体布局不再作为视觉要求。

## 1. 目标与完成原则

1. 成熟方案接管其职责内的全部入口，不以安装依赖、接入一个组件或增加一层包装作为完成。
2. 每项替换同时修改消费者、测试和必要的数据衔接，删除对应旧机制。阶段之间可以分批实施，单项交付不能留下两套同职责实现。
3. 保持当前桌面式导航、分组、文件夹、拖拽、普通与私密空间、导入、备份和同步能力，减少维护代码。
4. 新版运行路径只使用当前模型。已有有效数据通过明确转换或导入边界进入新结构；不清库，不丢弃图标、网址、私密内容或同步配置，不新增猜测性历史兼容。
5. 保存成功才更新已保存状态。预览、表单草稿和持久化数据有清晰边界，失败不能被显示成成功。
6. 完成以源码清理、行为验证和浏览器验收为依据，不以界面截图或构建成功单独判定。

“完整替换”按职责判断：共享状态与订阅由 Zustand 管理，保存型表单状态由 React Hook Form 管理，翻译由 i18next 管理，普通通知由 Sonner 管理，本机同步互斥由 Web Locks 管理。Repository 事务、同步合并规则、图片处理和私密加密属于项目业务，继续由业务代码实现。临时弹窗开关、拖拽过程和输入预览可以使用 React 局部状态，不再自建另一套状态或表单框架。

## 3. 技术替换范围与删除清单

### 3.1 Zustand：全部共享状态入口

- 采用 Zustand 的标准 Store 和 selector 用法，覆盖首页、设置、导航、搜索、Popup，以及初始化、刷新、保存、恢复、同步写入和私密会话变化。
- 组件按需要读取状态，不继续依赖首页订阅完整快照再逐层传递全部数据的模式。
- 所有持久化修改仍经过统一 Repository 事务；成功结果写入 Zustand。保存失败保留已保存状态，并把失败交给正确的反馈入口。
- BroadcastChannel 与页面恢复焦点负责通知其他页面重读持久化数据。它们调用同一组 Store actions，不维护第二份共享快照；保留 Repository 成功提交时的单一广播来源，删除旧 Store 的重复广播。
- 私密锁定、解锁、改密、移除保护以及资源缓存失效统一接入新状态入口，防止锁定后残留可访问明文。
- 各页面的私密解锁会话继续分别管理；跨页面通知不携带明文，也不把其他页面的解锁状态直接复制到本页。资源 Hook 直接依赖 Repository，不因读取资源而隐式启动 Store。
- 移除完整数据的 localStorage 快速副本及其读写机制，避免同时维护第二份数据状态；检查新标签页启动脚本，必要的主题元信息保持最小且不含业务或私密数据，并实测首屏表现。
- 不用 Zustand persist 自动保存整个业务 Store，IndexedDB 继续作为已保存数据来源。

**删除项：**自建 listeners Set、notify、模块级共享 snapshot、手写 React 订阅桥、旧 Store 兼容壳及其消费者；废弃快速缓存入口与读写。

**完成条件：**全部共享状态消费者和写入路径使用 Zustand；跨页面、恢复及私密操作仍正确；代码中不再存在第二套共享状态订阅机制。

### 3.2 React Hook Form + Zod resolver：全部保存型表单

| 表单       | 必须覆盖的入口                                   |
| ---------- | ------------------------------------------------ |
| 网站       | 首页添加／编辑、图标编辑、Popup 保存当前网站     |
| 同步       | WebDAV、GitHub、Gitee 配置与同步密码             |
| 私密保护   | 首页解锁、设置密码、修改密码、移除密码           |
| 搜索引擎   | 添加与编辑引擎                                   |
| 备份与恢复 | 导出空间及密码、恢复方式及解密密码、书签导入选项 |
| 导航对话框 | 保存名称、移动网站／文件夹／分组等提交型交互     |
| 外观提交   | 在线壁纸地址及其他需要明确提交、校验的设置       |

- 字段、错误、dirty、提交中、重置和服务端／业务错误使用 RHF 的标准 API；使用 Zod resolver 复用或组合业务 Schema。
- 受控 Radix/shadcn 控件按 RHF 的标准集成方式连接，不另外维护一份同字段表单状态。
- 默认值异步加载或外部状态刷新时不覆盖用户已修改字段；切栏目、关闭面板或切空间时，对未保存草稿提供统一的保留／放弃处理。
- 私密草稿遵循会话边界：主动离开前处理未保存输入，实际锁定后立即清除 RHF 字段与 defaultValues、密码、私密文件预览及 Object URL；不跨空间保留明文，也不因草稿确认延迟锁定。
- 提交期间禁止重复提交，失败保留字段和文件选择，错误显示在对应字段或表单错误区域。
- 网址沿用先 normalizeUrl、再校验的行为，保留缺省协议补全和原地址的路径、查询参数与片段；不因更换表单库改变已有有效输入规则。
- 搜索框即时输入、简单开关和滑块预览不是保存型表单，保留相应局部交互状态。

**删除项：**上述表单中重复的字段 useState、JSON.stringify dirty 比较、手写 submitting 状态机、FormData 解析及重复校验代码。文件处理、图片预览和业务命令不属于这些删除项。

**完成条件：**清单中的所有入口完成迁移；同一表单不同时运行 RHF 与旧字段／提交状态；错误、草稿和重复提交得到验证。

### 3.3 i18next + react-i18next：完整国际化路径

- 首页、设置、导航、搜索、时钟、引导、Popup、确认框、通知、同步状态和错误全部使用稳定语义键。
- 参数、数量和动态内容交给 i18next 插值与复数机制；用户自定义名称、网址和问候语作为用户数据展示。
- 业务错误使用明确错误标识和参数，在展示边界翻译；不再从中文错误句子反推含义。
- 同步持久化 lastError 与待处理冲突使用可翻译的业务描述，语言切换后能够重新渲染；未知外部错误可保留诊断详情，不把它当语义翻译键。
- 中英文资源覆盖同一组键。普通／私密空间语言与 Popup 的语言行为按现有有效设置统一初始化和切换。
- 覆盖启动／加载提示、ErrorBoundary 和下载模板；用户数据不翻译，浏览器 manifest 的原生 `_locales` 与 Intl 日期格式按各自职责保留。
- 测试覆盖键完整性、参数、切换语言及动态业务错误。缺键需要被检查发现，不能靠静默回退掩盖漏迁。

**删除项：**`t(language, 中文原文)` 旧接口、中文查表字典、动态错误正则、用于产品文案的语言三元分支，以及仅为这些机制服务的测试。

**完成条件：**所有产品文案与动态错误通过新机制展示；旧翻译入口零消费者，旧机制删除。

### 3.4 Sonner：全部普通操作通知

- 新标签页和 Popup 各自挂载所属页面的 Toaster；复制、添加、移动、删除、导入、导出、同步和壁纸等普通操作通知统一使用 Sonner。
- 统一成功／失败表达及翻译入口，不重复实现队列、定时消失、动画或通知容器。
- 字段错误由 RHF 就地显示；启动／数据库加载错误使用带重试入口的页面状态；持续同步状态仍在同步页面展示；危险操作继续使用 Radix AlertDialog。
- 设置连续保存显示轻量状态，不对滑块每个刻度弹通知；Popup 的保存成功页面仍是业务页面状态。

**删除项：**自建 notice、普通操作 message、通知容器、仅为转发普通通知而存在的 onError props 链。

**完成条件：**普通操作只有 Sonner 一套通知机制，表单和阻塞错误各归其正确的展示入口。

### 3.5 Web Locks：完整替换本机同步租约

- 在目标 Chrome/Edge/Firefox 扩展上下文检查 `navigator.locks` 支持；统一锁名和作用范围，所有同步入口使用同一互斥入口。
- 页面手动同步、后台 alarm 自动同步、上传覆盖、下载恢复、resolveSyncConflict，以及会改变连接、基线或同步密码的操作，按实际竞争范围纳入互斥或明确阻止并行。
- 使用标准申请与释放行为处理占用、取消和异常；不保留 browser.storage 读写回读租约作为备用互斥方案。
- 升级时只清理已知废弃的 `raytab-sync-lease`；不通过清除连接的函数清理租约，避免连带删除用户配置、基线和冲突。
- Web Locks 仅解决本机同源上下文竞争。Repository 事务、revision／updatedAt 校验、远端 ETag／SHA 条件写入及冲突处理继续保留。
- Web Locks 不作为 MV3 后台保活机制；页面关闭或后台终止后锁的释放、任务失败和重启恢复需要实际验证。远端写入成功而本地提交失败时明确报告并提供恢复路径，不能宣称自动回滚远端或获得跨设备原子事务。

**删除项：**LEASE_KEY、owner、expiresAt、租约获取／回读／释放流程，以及仅验证旧租约细节的测试。

**完成条件：**所有竞争入口使用同一标准锁；双页面竞争、异常释放和远端冲突验证通过；旧租约没有活动读写路径。

### 3.6 Playwright：实际执行的扩展交互回归

- 增加明确的 E2E 命令、测试配置、隔离浏览器 profile、测试数据和失败截图／trace。
- 使用 Playwright 自带 Chromium 的 persistent context 加载 `.output/chrome-mv3`，验证真实扩展页面和 Popup，不把 localhost 预览当作扩展验收。
- CI 构建扩展后执行关键回归；失败阻止检查通过。测试不得依赖用户实际账号、私密资料或远端同步配置。
- Vitest 继续覆盖模型、事务、合并、加密和错误场景；两类测试按职责分工。
- Firefox 保留构建和实际扩展验收。Playwright 官方扩展加载方案针对 Chromium，不能将普通 Firefox 网页测试写成 Firefox 扩展自动验收。

**完成条件：**测试真实执行并接入 CI，覆盖下文关键流程；Firefox 未自动化的部分明确标记，并提供实际加载验收记录。

### 3.7 保留的成熟基础

WXT、React、TypeScript、Tailwind、Radix/shadcn、Lucide、Simple Icons、idb、Zod、dnd-kit、Web Crypto 与 Vitest 继续使用。

本轮不替换 idb 为 Dexie，也不新增 Ky。当前数据库的大部分逻辑属于事务、修订、资源和私密业务；更换数据库 API 无法直接消除这些逻辑。请求层若以后存在确切重复机制，再单独决定是否整体由 Ky 接管。本次六项替换不因此缩减范围。

## 4. 网站图标初始方案（历史）

第 4—6 节保留最初的界面与数据衔接方案，用于追溯决策。此前的图标留白、右侧设置、逐行继承恢复及网站“…”入口已由后续产品研究和用户反馈调整，当前实现以第 9 节、[界面基准](ui-reference.md) 和 [当前验收](modernization-validation.md) 为准。

### 显示规则

| 类型     | 默认显示                                                             |
| -------- | -------------------------------------------------------------------- |
| 文字图标 | 允许编辑 1–4 个字，随底色自动使用可读文字颜色                        |
| 网站图标 | 复用品牌素材或获取并保存网站图片；无可用图片时显示名称首字           |
| 上传图片 | 保留素材原比例与自身背景，不增加统一白底或内边距；裁切由用户明确选择 |

- 单页网站编辑仅保留上述三种来源、文字输入和颜色选择；获取图标与网址同行，图片裁切按当前素材显示。删除完整图标／Logo 选择、重复预览及编辑页签；首页、文件夹缩略图和编辑选项使用一致显示规则。
- 常用品牌复用 Simple Icons 或清晰的完整官方素材，按实际域名匹配。通用网站选择合适的高分辨率图标并缓存；不因页面名称包含品牌词而错误套用 Logo。
- 图片自身带白边时允许换素材或明确裁剪，不自动抠白、失真拉伸或裁掉 Logo。
- 图标区域使用 React Easy Crop 的标准拖动、缩放、键盘和区域计算；裁切确认后经过现有图片处理及 Repository 保存，当前草稿可恢复未裁切图片。
- 普通悬停只轻量强调图标，移除关闭卡片背景时的大面积毛玻璃块及父子重复抬升。编辑按钮靠近图标；管理选中框、键盘焦点和拖拽反馈继续清晰。
- 全局设置直接展示图标尺寸、间距、每行数量、圆角和标题；减少用户需要组合“卡片大小＋图标比例”才能调整图标的情况。

### 数据衔接

- 采用单一的图标内容配置与独立底板配置。来源、文字或资源引用组成原子配置，底板独立配置；三方同步合并与冲突应用按同一口径处理，不同时保留两套图标字段作为运行路径。旧 display 字段仅在既有转换边界清理，网站图片和上传图片都纳入资源引用与备份。
- 同步修改 Schema、命令、默认网站、Popup、书签导入、资源引用与清理、私密资源、备份导出／恢复、同步基线／合并／冲突展示。
- 当前本地 appState.schemaVersion 为 4，备份 document.version 为 2；新增必需图标配置后，分别升级为新的明确格式，并针对这些已知格式提供一次转换边界。现有本地 v2／v3 转换只在该边界串联进入新结构，业务运行态不接受旧模型；不增加未经证实的更旧格式。保留当前资源字节、网址、顺序及颜色选择，转换失败保留原数据并给出明确错误。
- 同步基线中的 document、待处理冲突及解密后的私密内容同步转换。baseline.version 是远端 ETag／SHA，不是数据版本；IndexedDB 物理版本和 AES-GCM envelope.version 不因增加业务字段而机械升级。
- 加密私密明文目前没有自身版本；保留可识别的格式依据，在认证解密边界转换已知旧内容。普通空间同步透传旧私密信封时，不能因外层 document 升版就认定密文内部已经转换。
- 图标“恢复默认”需要解除资源引用并正确清理不再使用的资源；资源仍被其他网站或空间引用时不能删除。
- 未解决冲突的候选图片保存在可恢复的冲突上下文中，选择远端版本时按需恢复资源并与网站配置一起提交。验证“产生图标冲突→重载→选择远端图标”仍能显示图片，不能只从当前已选中资源快照取图而丢失候选素材。
- 测试样例包含截图中的知乎、哔哩哔哩、Google、GitHub、DeepSeek、ChatGPT、YouTube，以及透明、白底、长方形和损坏图片。

## 5. 设置界面初始方案（历史）

### 分类与控件

保留分类侧栏与内容区域的结构，按用户任务重组当前功能：

| 分类       | 内容                                                   |
| ---------- | ------------------------------------------------------ |
| 图标与布局 | 图标尺寸、间距、每行数量、圆角、标题、分组栏           |
| 壁纸与主题 | 壁纸来源、纯色／渐变、遮罩、文字配色、亮／暗／系统主题 |
| 搜索与时钟 | 搜索引擎、搜索栏、时钟、日期、农历、问候语             |
| 隐私       | 设置保护、修改／移除密码、私密空间设置继承             |
| 同步       | 连接表单、双向同步、状态与高级覆盖操作                 |
| 数据与备份 | 书签导入、备份空间、加密导出、预览和恢复               |

当时方案将语言放在分类栏底部，使用约 480px 的右侧面板。此布局已退役；当前为 840×640px 居中工作区，语言归入通用设置，不保留整页模拟预览。

- 控件统一使用 Radix/shadcn 的 Switch、Slider、Select、Input、按钮和标准表单集成。二元选项、枚举、连续值分别使用合适控件，不自建通用控件状态机。
- 设置行统一为名称、必要说明、当前值和控件；常用项直接显示，低频参数折叠。主题、壁纸及图标提供能反映实际效果的预览。
- 统一语义颜色变量，验证亮／暗／系统主题；统一字号和间距，小屏不横向溢出，长文案与键盘焦点可见。
- 网站外层卡片底板及不透明度设置完全删除；图标素材本身的背景由图标设置处理。导入默认方式、导出空间和恢复影响范围由当前值生成说明。

### 保存、草稿与私密继承

- 滑块调整使用即时预览；提交最终值时合并连续变化，不对每个刻度写库。鼠标、键盘、关闭面板和切空间均有明确的提交或保留处理。
- 同一设置保存入口处理顺序和失败，提交字段 patch，不用旧完整快照覆盖其他页面的新修改；显示“保存中／已保存／失败”，失败保留待保存值并可重试。
- 保存型表单统一使用 RHF；切栏目或关闭前保护未保存输入，保存期间阻止重复操作。
- 每项私密设置就地展示“跟随普通空间／已单独设置”和恢复入口，继续使用同一业务继承模型。
- 同步页突出双向同步，覆盖／恢复进入高级操作区并确认实际范围；备份恢复和删除沿用危险操作确认。

## 6. 右键与更多菜单初始方案（历史）

| 对象         | 目标菜单                                                     |
| ------------ | ------------------------------------------------------------ |
| 桌面空白     | 添加网站、新建文件夹、整理桌面、外观设置、简洁模式、全部设置 |
| 网站         | 编辑网站、更换图标、移动到、复制网址、删除                   |
| 文件夹       | 重命名、移动到、整理内容、解散                               |
| 分组         | 新建分组、重命名、前移／后移、删除                           |
| 时钟／搜索栏 | 打开对应设置；搜索输入区域保留正常的输入与浏览器菜单行为     |

- 网站“…”与右键展示相同动作；需要左键入口的对象提供更多菜单。复用 Radix ContextMenu 与 DropdownMenu，动作定义与业务处理只有一份。
- 桌面空白菜单覆盖真正的页面空白，简洁模式也可使用；网站、文件夹、分组只显示所属对象菜单，不误触父级菜单。
- 外观入口直接打开图标布局或壁纸栏目；更换图标直接定位同一网站编辑器的图标部分，时钟／搜索入口定位对应设置。
- 菜单关闭后焦点正确返回触发对象；键盘、触控和右键都有可用入口，输入框及设置表单保留正常编辑行为。
- 常驻设置与空间切换入口保留；进入整理后仍显示全选、移动、删除和完成工具栏，明确当前操作范围。
- 删除分组至少保留一个分组并处理内容去向；解散文件夹保留网站；危险操作确认不得因移入菜单而消失。

## 7. 实施阶段与交付门槛

阶段用于划分可验证的改动；单项技术只有满足完整覆盖、旧机制删除和行为验证后才能标记完成。

| 阶段                  | 工作                                                                                            | 进入下一阶段的条件                                                       |
| --------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 0：基线与验证准备     | 记录当前失败、数据与核心行为；建立隔离 Chromium 扩展测试及 CI 入口；检查目标扩展 Web Locks 支持 | 基线可复现；测试能加载真实扩展；已知失败有明确记录                       |
| 1：共享状态与同步互斥 | 全量替换 Zustand 和 Web Locks；改完首页、Popup、恢复、同步、冲突处理、后台自动同步与私密入口    | 旧 Store／租约删除；保存、跨页面、锁定／解锁、同步与冲突处理竞争测试通过 |
| 2：国际化与通知       | 全量替换 i18next 与 Sonner；转换业务错误与所有 UI 文案入口                                      | 旧翻译／通知机制删除；中英文、动态错误及各页面反馈通过                   |
| 3：表单与设置         | 所有保存型表单迁移 RHF；重组设置、统一控件、完成预览保存与草稿保护                              | 表单清单全部迁移；无重复字段／dirty／提交状态；设置关键流程通过          |
| 4：图标模型与显示     | 完成图标配置、完整数据衔接、素材及预览规则，收敛悬停                                            | 原有有效数据不丢失；备份往返、私密及同步图标验证通过                     |
| 5：菜单整合           | 完成桌面和对象菜单、更多菜单共用动作、设置定位                                                  | 右键／左键／键盘行为一致，拖拽与管理模式无回归                           |
| 6：最终验收与清理     | 完成 E2E、Firefox 实际加载、两个浏览器构建、文档与废弃机制审计                                  | 全部交付检查通过，限制如实记录；未完成的要求不得标记完成                 |

实现阶段通过 pnpm 增加上述已选定依赖，并同步更新 package.json、锁文件和依赖声明。单个阶段完成就清理该阶段的旧机制，不把“稍后删除兼容层”作为阶段交付。

无需为了整齐重排整个仓库，也不再建立额外通用 Store、表单、通知、菜单或翻译框架。使用库的标准能力和必要的业务组合。
